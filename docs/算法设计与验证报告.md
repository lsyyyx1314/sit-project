# 一、问题定义

给定 SDN 网络，控制器为源 s 到目的 t 维护候选路径集合 **P** = {P_1, …, P_k}。
数据包可能沿任一 P_j 转发，逐跳更新一个定长验证头 H。出口交换机把 H 上报控制器，
控制器需判定：

> 该包实际经过的路径是否属于 P ？

需要同时满足四个约束：

| 编号 | 约束 | 来源 |
|---|---|---|
| C1 | 定长：\|H\| = O(1)，与跳数 n、路径数 k 无关 | 申报书式 (4) |
| C2 | 顺序绑定：路径顺序改变必须导致验证失败 | 申报书「非交换性」 |
| C3 | 低开销：控制器判定不应随 k 线性膨胀 | CPMV 目标 |
| C4 | 不可伪造：中间交换机篡改转发后不能自洽 | 安全前提 |

符号：n 为跳数，k 为候选路径数，p 为域素数，H(·) 为公开哈希。

# 二、原构造的缺陷与根因

## 2.1 现象

申报书式 (5)：

    g^(w·s_m) mod p2 = f_s^w mod p2 ,   w = lcm(p1−1, p2−1)

由欧拉定理，w 是 p2−1 的整数倍且 gcd(g, p2)=1，故 g^w ≡ 1 (mod p2)。而
f_s = g^(Σ s_i·r_i)，于是 f_s^w ≡ 1。**两端恒为 1**。

`sim/counterexample_r1.py` 在 16/32/64 位三档参数下各做 200 次随机试验，
伪造包接受率 100%，诚实流通过率 0%。

## 2.2 根因

不是参数没选好，而是方法论问题：

> **模幂是指数上的加法结构，随机数 r_i 一旦进入指数，就无法在不暴露 r_i 的前提下被消去。**

任何「先在指数里加随机量、再用统一指数把它抹掉」的写法都会落入同一个陷阱：
抹掉随机量的同时，路径信息也被一起抹掉了。

## 2.3 结论

R1 不能靠调参关闭，必须换承载结构。可行方向只有一个：

> **把随机性放在线性项上，让控制器可以直接代入，而不是事后消去。**

# 三、MPV-2 构造

## 3.1 参数

| 符号 | 取值 | 说明 |
|---|---|---|
| p | 2^64 − 59 | 64 位素数，保证累加值恰占 8 字节 |
| ρ | 0x9E3779B97F4A7C15 mod p | 公开底数，用于位置加权 |
| H(·) | blake2b → Z_p | 公开哈希，任何人可算 |
| (a_i, b_i) | PRF(k_si, "a"/"b") → Z_p² | 由式 (2) 端口密钥派生 |
| nonce | 56 bit 随机 | 逐包生成 |
| tag | 8 bit | 路径编号，由背离点组表 bucket 写入 |

## 3.2 验证头

    H = (nonce, V, tag),   |H| = 7 + 8 + 1 = 16 字节（恒定）

## 3.3 数据平面

单跳贡献：

    h   = H(nonce)
    c_i = (a_i + b_i · h) mod p

入口交换机（第 1 跳）：

    V = c_1

第 i 跳（i ≥ 2）：

    V ← V + c_i · ρ^(i−1)  mod p

即 V = Σ_i c_i · ρ^(i−1)。

## 3.4 控制平面

对候选路径 P_j 预计算（与 nonce 无关，流建立时完成一次）：

    A_j = Σ_{i∈P_j} a_i · ρ^(i−1)  mod p
    B_j = Σ_{i∈P_j} b_i · ρ^(i−1)  mod p

逐包判定只需代入 h：

    E(h, P_j) = A_j + B_j · h  mod p
    验证通过  ⇔  V = E(h, P_j) 且 tag = j

## 3.5 三种判定模式

| 模式 | 依据 | 复杂度 | 适用 |
|---|---|---|---|
| tag 模式 | 只查 tag 指向的那条路径 | O(1) | 默认，tag 可信 |
| scan 模式 | 遍历全部候选 | O(k) | tag 可能被破坏时的兜底 |
| 流级模式 | 按 tag 分组累加 | O(条目数) | CFMV |

## 3.6 流级压缩（CFMV）

E(h) = A + B·h 对 h 线性，因此对同一路径上 N 个包求和：

    ΣV = Σ(A + B·h_i) = N·A + B·Σh   (mod p)

出口交换机按 (流, tag) 聚合三元组 `(N, Σh, ΣV)`——h(nonce) 出口侧可直接重算——
凑满一个窗口上报一行 `FLOW`（`--flow-window`，退出前冲刷残窗）。控制器判定：

    N·A_P + B_P·Σh ≡ ΣV   (mod p)

- 每窗口一次判定，与窗口内包数 N 无关（N=4096 实测 0.04 µs，k=16）；
- 上报体积由每包一行降为每 (流,tag,窗口) 一行，N 包 → ≤k 条；
- 聚合域内动任何一个分量（ΣV、Σh、N）都会破坏恒等式，单元测试覆盖。

**安全边界（必须配合重放窗口）**：聚合是可加的，重放一个合法包能同时抬高
(N, Σh, ΣV) 且恒等式依然成立。因此控制器为每个方向维护 `NonceWindow`
（定长环形缓冲，容量 4096），nonce 重复的包在进入判定前直接标记为重放丢弃。
CFMV 的安全性陈述为：「非重放的篡改以 1/p 概率通过窗口判定；重放被 nonce
窗口完全拦截」。

# 四、正确性与安全性

## 命题 1（完备性）

若包沿 P_j 转发且 tag = j，则验证必通过。

证明：由 3.3，V = Σ_{i∈P_j} (a_i + b_i·h)·ρ^(i−1) = A_j + B_j·h = E(h, P_j)。∎

## 命题 2（顺序绑定）

若 P' 是 P_j 交换任意两跳顺序得到的路径，则 V 不再通过 P_j 的判定。

证明：交换第 u、v 跳（u<v）后，两项的权重从 ρ^(u−1)、ρ^(v−1) 变为 ρ^(v−1)、ρ^(u−1)，
差值为 (c_u − c_v)(ρ^(v−1) − ρ^(u−1))。该式为零当且仅当 c_u = c_v 或 ρ^(v−1) = ρ^(u−1)，
前者要求两跳密钥巧合、后者要求 ρ^(u−v) ≡ 1（ρ 的阶远大于 n，实际不发生）。∎

## 命题 3（不可伪造性）

设路径上至少有一跳诚实。攻击者掌握若干被攻陷跳的 (a_i, b_i)，但不知道诚实跳的密钥。
若攻击者要让沿 P' 生成的 V' 通过 P_j 的判定（P' ≠ P_j），必须令

    V' − (A_j + B_j·h) ≡ 0

而 A_j、B_j 含诚实跳的未知密钥，故 V' 落在正确值上的概率不超过 1/p = 2^−64。

证略（标准的一次性猜中论证）：对攻击者而言 A_j + B_j·h 在 Z_p 上近似均匀，
其可控制的部分至多覆盖一个仿射子空间，命中单点的概率为 1/p。∎

## 命题 4（集合判定完备性）

若包沿合法路径 P_j 转发，scan 模式必返回 j；若沿集合外路径转发，scan 必拒绝
（除 1/p 的碰撞概率）。

## 命题 5（流级正确性）

同一 tag 下 N 个包的累加值满足 ΣV = A_j·N + B_j·Σh。
证明：V_p = A_j + B_j·h_p 对每个包成立，逐项求和即得。∎

## 4.6 明确的假设与边界

必须写清楚，避免过度声称：

1. **控制器持有全部密钥**。这是集中式验证的固有前提，控制器被攻破则方案失效。
2. **至少一跳诚实**。全部跳被攻陷时，攻击者可自洽伪造，任何路径验证方案都如此。
3. **不抗重放**。同一 nonce 的合法旧包可被重放并通过验证。需要 nonce 缓存窗口或
   时间戳，属于部署层问题，不在本构造范围内。
4. **抗 DoS 能力有限**。攻击者可以任意扰动 V 使验证失败（只能造成拒绝，不能伪造）。
5. **tag 未单独认证**。tag 被篡改会导致验证失败，安全性由 V 承载，不依赖 tag 本身可信。

# 九、端到端验证（M2）

算法层验证只能说明「构造自洽」，不能说明「在真实转发上成立」。本节把 MPV-2
放进虚拟交换机，跑真实以太帧收发。

## 9.1 为什么自己写交换机

OVS 的动作集只有 `set_field` / `add` / `group`，**没有模运算**，无法计算
`c_i = (a_i + b_i·H(nonce)) mod p`。BMv2 的 ALU 是 32 位，跑不了 64 位模域。

因此数据面实现为**用户态软件交换机**（`mpv/dp/vswitch.py`）：AF_PACKET 多端口收发，
按预置转发表转发，每跳执行一次模乘加，验证头以 16 字节垫片（ethertype 0x88B5）
插入以太头之后，出口交换机剥离并恢复 0x0800。

这不是权宜之计：MPV-2 的逐跳更新本质就是一个可编程数据面动作，
软件交换机是它最直接的落地形态。

## 9.2 拓扑与实验设计

        h1 --- s1 --- s2 --- s4 --- h2
                 \            /
                  +--- s3 ----+

正向 P0 = [s1,s2,s4]，P1 = [s1,s3,s4]；反向同理。四台交换机各自独立进程。

| 轮次 | 设置 | 预期 |
|---|---|---|
| R1 正常 | 转发表与路径一致 | 全部通过 |
| R2 故障 | s1 的 tag=0 条目改走 P1 分支，下游表同步改，使错标路径在数据面自洽 | 全部失败，且能定位 |

R2 故意做成「自洽的错标」：如果只是把包丢错端口，任何方案都能发现；
真正难的是包沿一条**合法但非声称**的路径完整走完。这正是 CPMV 要解决的场景。

## 9.3 结果

```
[R1 正常转发]  出口上报 40 条
  正向 h1→h2: 通过 20 / 失败 0 / 共 20
  反向 h2→h1: 通过 20 / 失败 0 / 共 20

[R2 标签错配]  出口上报 40 条
  正向 h1→h2: 通过 0 / 失败 20 / 共 20
      → 实际命中候选 #1，标签声称 #0：路径标签错配，分歧点 s1（20 条上报全部一致）
  反向 h2→h1: 通过 20 / 失败 0 / 共 20
```

三点值得注意：

1. **双向独立验证**：正反两个方向各自 20 条，互不干扰。
2. **R2 反方向全过**，说明故障注入只影响被改的那一侧，检测没有"连坐"——这是
   判定是否有误报的直接证据。
3. **定位落到 s1**：控制器扫描候选集发现 V 命中 P1，而 tag 声称 P0，两条路径的
   最后一个共同交换机就是 s1，即错误下发的位置。

## 9.4 端到端仍不是"性能实测"

必须区分：

| 数据来源 | 是什么 | 能不能当性能结论 |
|---|---|---|
| `sim/bench_scheme.py` | Python 算法耗时 | 只能说明相对量级 |
| `exp/e2e_verify.py` | 真实帧收发，但每包一次用户态处理 | 功能验证，不是吞吐量测 |

用户态交换机每包要进出内核一次，吞吐量比硬件低两三个数量级。所以本节的结论
严格限定为**功能正确性与定位能力**，吞吐/时延仍需 P4 或 DPDK 形态才能给。

# 十、C++ 实现与跨语言交叉校验（M2.5）

## 10.1 为什么迁到 C++

第一版是 Python。它的价值在于快速把数学跑通，但有两个硬伤：

1. **性能数据失真**：Python 的模乘要经大整数对象，判定时延 1.6 µs 中有很大比例是
   解释器开销，无法与任何硬件实现对话；
2. **数据面保真度低**：用户态交换机在 Python 里每包要分配对象，吞吐被压到几十 kpps。

迁到 C++17 后，判定时延降到 **0.27 µs**，且整个工程不再依赖解释器与第三方包。

## 10.2 依赖策略

刻意**不引入任何外部库**：

| 需求 | 选择 | 理由 |
|---|---|---|
| 密码学哈希 | 自实现 BLAKE2b（RFC 7693） | OpenSSL 的 EVP 只暴露 digest_size=64，而方案需要 keyed + 8 字节 |
| 大整数模乘 | `unsigned __int128` | 64 位模域恰好够用，不需要 GMP |
| 网络数据面 | 原生 `AF_PACKET` | 不依赖 libpcap/OVS |
| 拓扑 | `ip netns` + `veth` | 不依赖 Mininet（Python） |

结果：`make` 一条命令，`g++ ≥ 11` 即可编译，零运行时依赖。

## 10.3 跨语言交叉校验

迁移最大的风险是「重写之后悄悄算错了，但所有测试都通过」。因此把 Python 版**冻结成
预言机**，只做一件事：生成黄金向量。

`cpp/tests/golden_vectors.txt` 包含：

| 类型 | 条数 | 内容 |
|---|---|---|
| HOP | 192 | 每跳的 `port_key`、`(a, b)` |
| PATH | 3 | 每条路径的 `A`、`B` |
| VEC | 15 | 每条路径 × 5 个 nonce 的 `h` 与 `V` |

C++ 侧 `make test` 逐项比对：

```
== 1. 黄金向量交叉校验（C++ vs Python 参考实现）==
   已比对 612 项
== 2. 功能与对抗断言 ==
   新增 12 项

结果：通过 624，失败 0
```

**612 项逐位一致**，其中包含自研 BLAKE2b 与 Python `hashlib` 的输出对齐。这比"两边各跑
一遍看结果像不像"强得多：任何一个字节的偏差都会当场失败。

## 10.4 端到端仓也换成 C++

原来的端到端用 Mininet 搭建拓扑，而 Mininet 本身是 Python 库。为彻底去掉解释器依赖，
拓扑改用 `ip netns` + `veth` 直接搭建（`cpp/scripts/e2e.sh`），交换机与验证器都是
C++ 可执行文件。

同一套两轮实验（R1 正常 / R2 标签错配），结果与 Python 版一致：

| 轮次 | 正向 | 反向 | 结论 |
|---|---|---|---|
| R1 | 20/20 通过 | 20/20 通过 | 无误报 |
| R2 | 0/20 通过 | 20/20 通过 | 检出并定位到 s1 |

## 10.5 迁移过程中踩到的坑（记录以备复查）

1. **AF_PACKET 的 `send()` 不够**：绑定了接口的 SOCK_RAW 直接 `send()` 会失败，
   必须用 `sendto()` 传 `sockaddr_ll`（含 `sll_ifindex` 与目的 MAC）。
2. **会收到自己发出的帧**：`recvfrom` 的 `sll_pkttype == PACKET_OUTGOING` 必须过滤，
   否则自环风暴。
3. **veth 两端都要 up**：只 up 一端时 `sendto` 报 `Network is down`，现象是交换机
   收到包但一帧也转发不出去。
4. **netns 会发 IPv6 ND**：不关掉 `net.ipv6.conf.all.disable_ipv6` 会混入 0x86dd 帧，
   干扰计数器与判定。
5. **攻击矩阵的自我验证陷阱**：第一版把"篡改后的头"拿去和"篡改后的路径"比对，
   得到 0% 检出率。正确做法是用**合法路径的表**去验证被篡改的包。这类错误只有
   对照诚实样本接受率才能发现。

## 10.6 最终形态：工程内无脚本语言

迁移分两步完成：

1. 先把算法与数据面换成 C++，Python 退居 `legacy/` 充当预言机；
2. 再把端到端编排也换成 C++（`cpp/src/e2e.cpp`），并删除整个 `legacy/` 目录。

现在仓库里**没有任何 `.py` 或 `.sh` 文件**，`git ls-files | grep -c '\.py\|\.sh$'` 返回 0。
端到端由 C++ 可执行文件 `e2e` 直接 `fork/exec` 拉起 4 个交换机进程，用 iproute2 的
`ip` 命令建命名空间与 veth——`ip` 与 `ping` 是操作系统工具，不属于工程代码。

代价是黄金向量失去了生成器。它已被冻结为 `cpp/tests/golden_vectors.txt`（213 行、
612 个比对点），作为不可变的回归基线使用；若将来需要重算，需按报告第三节的公式
重新实现一遍参考模型——这恰恰说明它作为"独立第二实现"的价值：**它不依赖被测代码**。

# 十、异常交换机定位（M4）

判定失败只回答「有没有问题」，定位回答「问题在哪」。工程实现分两层（多故障
升级见 10.4）：

## 10.1 逐跳取证定位（精确到交换机）

交换机以 `--trace` 开启取证模式：每处理一个带验证头的帧，就把本跳处理后的
实际累加值记为一行

    TRACE <dst> <sid> <in> <out> <tag> <nonce> <pos> <V_after>

控制器对失败包沿**声称路径**逐跳重算前缀期望 E_j = Σ_{i≤j} c_i·ρ^(i−1)，与
该交换机的取证值对照：

1. 某跳没有取证记录 → 包没能到达该跳，嫌疑 = 该跳（黑洞/静默丢弃）；
2. 某跳取证值 ≠ 前缀期望 → 从该跳起行为异常，嫌疑 = 该跳；
3. 全部匹配但出口上报值 ≠ E_L → 出口上报本身被篡改，嫌疑 = 出口。

定位是**精确到交换机**的：s2 比特翻转场景中，s1 的取证值正常、s2 的取证值
= E_2 ⊕ 1 ≠ E_2，嫌疑即 s2（双向均验证）。无取证时退化为候选对比：声称
路径与 scan 实际命中路径的首个分歧交换机。

## 10.2 黑洞（半路失联）定位

包死在半路时出口不会有上报——控制器改用集合差：**取证里出现过、出口却没有
上报的 nonce = 失联包**。对每个失联包做 10.1 的前缀对照，首个取证不匹配的
跳即改道交换机。演示中 s1 把 tag0 改道 s3（s3 无表项丢弃），20 个包全部
失联且全部定位到 s1。

## 10.3 定位的假设边界

取证值由交换机自己报告——被完全攻陷的交换机可以伪造一致的取证链。定位结论
的可信度以「多数跳诚实」为前提；这是遥测类方案的共同边界，论文中如实陈述。

# 十二、与已有方案的解析对比（M5）

|---|---|---|---|---|---|

## 10.4 多故障定位（升级）

单点定位只报首个嫌疑；`localize_all` 沿实际取证路由逐跳对照，同时报出**全部**嫌疑：

* **篡改嫌疑**：期望值以「上一跳的观测值」为基准（carry = 上一跳 V_after）。
  篡改偏移 δ 会随帧传播，若用纯净累计值对照，会把下游诚实交换机也误标——
  观测值基准让 δ 只影响紧随其后的一次比较；
* **改道嫌疑**：实际 (sid,in,out) 与声称路径第 i 跳不一致 → 声称路径第 i 跳
  交换机为改道嫌疑；此后位置对照关闭，仅继续篡改对照；
* **出口上报嫌疑**：仅当取证全程吻合声称路径、无其他嫌疑、而最终上报仍不符
  时，才判定出口上报本身被篡改。路由已偏离或已有篡改嫌疑时，上报值不等属于
  正常推论——此条件过宽会把无辜的出口交换机卷入嫌疑集（实测教训，已修）。

端到端 R7（标签错配 + s3 比特翻转双故障）实测：20/20 检出，嫌疑集合 {s1, s3}，
反向方向零误报；合成向量单测覆盖 {改道, 篡改} 组合（tests 700 项断言）。

## 10.5 链路故障切换（验证与重路由协同）

多路径验证在动态重路由下的正确性是独立问题：候选集若不随拓扑收敛，切换后
全部流量都会被误判。failover 场景实现协同流程：

1. s1–s2 链路物理 down（`ip link set down`，两端）；
2. 控制器候选集收敛：{P0, P1} → {P1}，期望表按场景重建；
3. 转发表热加载：tag0 全网改走 P1 分支（s1→s3→s4，反向 s4→s3→s1）；
4. 流量切换后验证继续全通过、零误报（e2e R6 实测；浏览器场景同）。

该场景同时回答了一个隐含问题：验证机制的「合法路径集合」不是静态配置，
而是控制器全局视图的函数——重路由改变合法集合时，验证必须同步收敛，
否则误报即「验证系统自身的故障」。
## 12 结题补充实验（M5.10）：项目书指标缺口补全

对照申报书要求的评估指标（验证准确率、控制器计算开销、**交换机存储开销**、
验证头大小、通信开销、**异常定位成功率**、**不同规模/路径数量**、**与现有方案
对比**），原 exp 套件缺四项，本次补全（exp [8]–[11]，数据见 `results/exp_report.md`）：

### 12.1 [8] 状态存储开销

口径：条目数 × 字段宽（结构定义可直接复核），非进程 RSS，保证方案间可比。

* 控制器期望表 O(k)：k=64 时 1 024 B + 路径索引 5 376 B = 6.4 KB；
* nonce 重放窗口定长 32 KB/方向（容量 4096，与速率无关）；
* 出口 CFMV 聚合 24 B/流，为逐流路径记录式（8B×h）的 1/2.3；
* 数据面转发路径 0 逐流状态——逐流状态只出现在出口聚合与 nonce 窗口。

### 12.2 [9] 异常定位成功率（大样本系统化）

随机路径 5–9 跳、随机故障位置，2000 样本（单故障/双故障/诚实对照）：

| 故障类型 | 样本 | 嫌疑集精确命中 |
|---|---|---|
| 恶意改头 | 486 | 100% |
| 路径改道（改端口/旁路） | 502 | 100% |
| 双故障（改头+改道） | 512 | 100% |
| 诚实对照 | 500 | 误报 0 |

真值口径：篡改跳 = 实际路径该跳 sid；改道跳 = 声称路径首分歧跳 sid；
命中 = 嫌疑集合与真值集合相等。1500 个故障样本全部精确命中、零误标。

**取证适用边界对照**（k=4 候选集）：合法集合内改道（tagflip）有/无取证均可
定位（100%/100%）；**集合外篡改只有逐跳取证能定位（100% vs 0%）**——这给
`--trace` 的存储开销一个明确的工程定位：买的是"闭集之外的可定位性"。

### 12.3 [10] 算法级基线对比（同测试床）

与 MPV-2 共用同一密钥体系与攻击样本的两个基线：

* **逐跳 MAC 链（Icing 类）**：判定时延随 k 线性，k=64 时 482.8 µs vs
  MPV-2 tag 模式 0.43 µs（≈1120×）；验证头逐跳追加 8B/跳。
* **概率采样多路径（Atlas 类）**：检出率 ≈ ρ。控制器判定负载 1/64 时
  漏检 98.4%；MPV-2+CFMV 同负载下 100% 检出——流级聚合与采样式"以漏检换
  负载"是两条不同的路：CFMV 不漏检。

### 12.4 [11] 规模扩展

h ∈ {4,8,16,32}：数据面单跳均摊 1.72–1.81 µs（O(1) 不随 h 变化）；控制器
tag 判定恒定 0.33 µs 与 h 无关；期望预计算随 h 线性（5.7→45.4 µs）但仅为
流建立时一次；检出率 100% 不随规模退化。

## 13 安全修补与数据面深度（M5.11）

对本工程做逐文件安全/健壮性审计后，修复以下缺陷（tests 712 项断言全部通过，
含新增 12 项回归断言）：

### 13.1 nonce 可预测性（高危，已修）

**缺陷**：vswitch 以 `srand(seed ^ sid) + rand()` 生成 nonce——同 seed 每次启动
产生**完全相同的 nonce 序列**。验证头只依赖 (nonce, 路径, 密钥)，因此上一轮运行
中录制的帧在控制器重启（重放窗口清空）后可以**永久重放且必然通过判定**：
重放防护对"跨启动"这一最基本的对抗场景失效。

**修复**：改用内核 CSPRNG（`getrandom(2)`），56-bit nonce 空间，跨启动不重复；
`--seed` 仅用于密钥派生。测试面：黄金向量与端到端全量回归无回归。

### 13.2 NonceWindow 判重绕过与 O(W) 扫描（已修）

**缺陷一（绕过）**：旧实现 `ring_[idx] == nonce && ring_[idx] != 0` 对 nonce==0
有特例——重放 nonce 为 0 的帧**永远**不会被检出。

**缺陷二（性能）**：判重为 O(W) 线性扫描，容量 4096 时每包约 2000 次比较。

**修复**：环形缓冲（到达顺序，用于老化淘汰）+ 哈希集合（O(1) 判重），
删除 0 特例。语义不变：容量 W 内重复判重放；被淘汰的陈旧 nonce 再次出现按
新包处理。实测（bench，容量 4096）：新 nonce 判重插入 **43 ns/次**（原线性
扫描 µs 级），窗口内重放检出 1000/1000。正确性以 10000 次随机操作影子模型
（朴素向量窗口）逐操作对照断言。

### 13.3 重放的语义边界（文档化）

* **窗口内重放**：逐包口径由 NonceWindow 拦截；CFMV 口径下重放抬高可加三元组，
  同样由窗口去重保证不叠加（端到端 R4 实测 60 条重放全拦截、诚实包零误伤）。
* **陈旧重放（超出窗口容量）**：被淘汰后按新包处理。此时重放的是**合法帧的
  复制**——它确实走过合法路径，判定为"通过"在路径语义上正确，后果是重复记账/
  重复交付而非路径违规。工程含义：**窗口容量必须 ≥ 最大乱序/缓存深度**；
  逐包口径若要求更强语义，需配流量表去重（超出本项目范围）。
* **跨启动重放**：由 13.1 的 CSPRNG nonce 关闭（nonce 不重复 ⇒ 旧帧的
  (nonce, V) 对在新窗口中仍是首次出现，但其 V 与新 nonce 的期望无关，
  判定必然失败——因为 acc 是用旧 nonce 算的）。

### 13.4 控制器侧资源治理

* `localize_all` 无取证回退路径此前每次**重建**期望表（O(k·h) 期望重算），
  改为复用构造时已构建的 `tables_[dir]`——定位路径上的一次纯浪费消除；
* 逐跳取证表 `traces_` 无上界，长期在线会无界增长；加 2²⁰ nonce 条目上界，
  溢出按世代清空（旧取证的包退化为候选对比定位，功能不中断）。

### 13.5 多实例隔离

e2e 与 dashboard 此前共享 `/tmp/mpv_run` 与 h1/h2 命名空间名，只能单实例运行。

## 14 演示控制台与交换机守护的健壮性（M5.12）

对 dashboard（HTTP 服务）与 vswitch（常驻进程）做并发/信号/数据一致性审计，
修复 5 项（curl 全 API 冒烟 + SIGTERM 清理检查实测通过）：

### 14.1 信号处理安全（dashboard + vswitch）

**缺陷**：两进程都在信号处理函数里做非异步信号安全的事——dashboard 的
`on_term` 直接调 `system()`（ip 命令清理拓扑）与 STL 析构；vswitch 的
`on_term` 在 handler 里 `fflush`/`fprintf` 上报文件，与主线程正在进行的
`fprintf` 并发是未定义行为（可能死锁或写坏上报行）。

**修复**：handler 只做异步信号安全的最小动作——dashboard 用自管道
（handler `write` 1 字节，主循环 `poll` 监听套接字 + 管道，唤醒后在主线程
停交换机、清拓扑）；vswitch handler 只写原子标志，主循环（200ms 轮询）
退出后由主线程 `flush_flows()`。冒烟实测：SIGTERM 后进程退出、netns/veth
零残留、未满窗口的流级聚合正常落盘。

### 14.2 流量计数竞态（dashboard）

**缺陷**：`/api/traffic` 先累加「已发送包数」再 CAS 抢占执行权——被并发
拒绝的请求也被计数，UI 数字虚高。

**修复**：CAS 成功（worker 真正接手）后才计数。

### 14.3 并发连接上限（dashboard）

accept 循环每连接一个分离线程、无上限；慢连接可无限占线程。加 32 并发
上限，超出直接回 503 并关闭。

### 14.4 HTTP 规范性（dashboard）

`/api/state` 此前无 `Content-Length`（依赖连接关闭定界）；补齐。另核对全部
端点：未知场景 400、未知路径 404、场景名白名单校验、count 限幅 1–500。

### 14.5 UI 内嵌基准数据与实测报告同源

页面内嵌的「判定时延 vs k」折线数据是早期一轮 bench 的硬编码（tag 0.21–0.35µs
与最新实测 0.31–0.33µs、scan k=64 0.76µs 不符）。更新为最新正式实测值并标注
数据来源，消除「演示数字与报告不一致」。

## 15 数据面性能剖析（M5.13）

### 15.1 方法

新增 `exp --flood N` 单项测量模式（只跑 h1→h2 ping 洪灌，写
`results/flood_report.md`，不触碰结题报告），同机同参数多次取中位，
用于优化前后的受控对比。

### 15.2 每包成本拆解（vswitch 热路径）

一次"帧进帧出"依次是：recvmmsg 收包 → 解析/查表 → `contribution` 一次模乘
+ `h_of` 一次哈希 → 组帧 → `sendto` → TRACE/FLOW 行写入。剖析发现三处
与验证计算无关的开销：

1. **每包堆分配**：目的/源 MAC 各构造一个 `std::string`（源 MAC 甚至从未
   被使用）、转发表键每包拼两次 string、流聚合键再拼一次——每包 5 次以上
   堆分配；
2. **每包 `fflush`**：TRACE 与出口上报行各 flush 一次，每包 1~2 次 syscall，
   是热路径上最密集的系统调用；
3. **每帧一次 `recvfrom`** 与 **逐包模幂 `powmod(ρ, pos−1)`**（~64 轮循环）。

### 15.3 优化

* MAC 全程以 48-bit 整数参与查表与聚合（键 = mac48<<8|tag），输出时才格式化
  到栈缓冲；删除未使用的 src 字符串——**每包零堆分配**；
* `recvmmsg` 批量收包（32 帧/syscall），批次不满即回 poll；
* ρ 的幂构造时预计算成表（位置有界），转发热路径查表 O(1)；
* `fflush` 从每包改到 **poll 轮次末按脏标志统一冲刷**——帧到达至 tailer
  可见的延迟仍 ≤ 一个轮次（200ms，tailer 轮询 120ms），上报语义不变。

### 15.4 实测（同日同参数各 3 次，10000 包洪灌）

| 版本 | 三次测量（行/秒） | 中位 |
|---|---|---|
| 优化前 | 2874 / 2714 / 2636 | **2714** |
| 优化后 | 3326 / 3078 / 2823 | **3078（+13%）** |

### 15.5 剩余瓶颈与结论

优化后每上报行墙钟仍 ~290µs。一次端到端管线 = 3 台交换机转发 + 6 次 veth
内核往返 + ping 进程本身；单交换机用户态计算（收发 syscall + 验证计算 +
行格式化）合计仅 ~2–5µs，**>90% 的墙钟在内核路径（veth 唤醒/调度）**。
结论：用户态 AF_PACKET 原型的吞吐上限由内核路径支配，数据面验证计算本身
（每跳 1 次模乘 + 1 次哈希）远未成为瓶颈——这也正是"控制器判定与数据面
解耦"架构论点的定量注脚，以及把验证逻辑下沉到 P4/硬件数据面的动机。

回归：tests 712/712、e2e R1–R7、dashboard 冒烟（tagflip fail=20 嫌疑 [s1]）
全部通过——优化不改变任何可观察行为。

## 16 计算时间优化：逼近不动方案语义的下界（M5.14）

### 16.1 微基解析：时间花在哪

以探针对 verify_tag（0.33µs 级）做成本分解，结论：**公开哈希 h_of 占 99%**
（367/371ns），模运算层已被编译器优化到位（128-bit 取模 6.6ns）。因此唯一
值得动的实现层就是哈希本身与"每次判定调用几次哈希"。

### 16.2 五项实现层优化（全部不改变任何输出，黄金向量逐位回归把关）

1. **blake2b 压缩函数重写**：12 轮完全展开（SIGMA 变编译期字面量，消息字
   无运行时查表）+ 消息块小端 64 位字 `memcpy` 装载（每块 128 次字节迭代
   → 单条 mov）。函数语义逐位一致；
2. **P = 2^64−59 广义梅森折叠**：mulmod/addmod 用 2^64 ≡ 59 恒等式折叠
   （6.6→3.1ns、8.7→2.6ns），回卷边界显式处理并新增对抗性正确性断言；
3. **公开哈希复用**：verify_tag/verify_scan 增加预计算 hh 重载——控制器
   双口径判定从 3 次哈希降为 2 次；
4. **hop_key 备忘录**：同一 (sid,in,out) 的密钥派生（3 次 blake2b）只做一次，
   数据面每跳与期望预计算查表 O(1)；
5. **上报解析快路径**：feed 前缀分发去掉每行两次 istringstream，逐包行
   手写解析（sscanf ~420ns → 手写 ~100ns）。

### 16.3 实测前后（VM 同方法学，10000 次样本/中位数）

| 指标 | 优化前 | 优化后 | 提升 |
|---|---|---|---|
| tag 模式判定（任意 k） | 0.31–0.33 µs | **0.23–0.25 µs** | ~1.4×，吞吐 303→400 万次/秒 |
| scan 模式 k=64 | 0.76 µs | **0.43 µs** | ~1.8×（折叠在 64 次迭代上放大） |
| 控制器上报吞吐 [4b] | 7.7 万行/秒 | **175.5 万行/秒** | **22.8×**（单行 12.99→0.57µs） |
| 期望预计算 h=32 [11] | 45.4 µs | **0.80 µs** | **57×**（备忘录 + 折叠） |
| 数据面单跳均摊 [11] | 1.7–1.8 µs | 0.18–0.34 µs | ~6× |

检出率/诚实接受/定位成功率全部不变（100%/100%/1500/1500 精确命中）。

### 16.4 下界论证：为什么这已是不动方案语义的极限

优化后单次 tag 判定 = **1 次 h_of + 1 次折叠乘 + 1 次折叠加 + 1 次比较**：

* 公开哈希 H 是方案定义的一部分（随机性搬到线性项的构造前提），RFC 7693
  的 12 轮压缩不可减——换更弱的哈希（如 splitmix）或减轮数会破坏随机
  预言语义，且使冻结的黄金向量交叉校验失效；
* 域运算已到 5ns 级（三次折叠乘法 + 条件减），再往下是硬件指令的事；
* 数据面每跳 = 1 次哈希 + 1 次模乘 + 1 次加法（密钥派生已被备忘录消除），
  且 §15 已证内核往返占墙钟 >90%——数据面亦无实现层油水。

即：**实现层已无开销可削；再往下只能改方案语义**（以安全性与可验证性为
代价）。这一结论本身就是本节的方法学产出。
