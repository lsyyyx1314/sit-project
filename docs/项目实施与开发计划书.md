# 一、申报书解构

## 1.1 一句话定位

把"验证一条固定路径"扩展为"验证一个合法路径集合"，在验证头不膨胀、控制器不超载的前提下，做到**能验证、验证快、开销低、可定位**。

申报书把研究问题拆成四个问句：如何验证、如何降低开销、如何保持一致性、如何定位异常节点。后续全部模块设计都围绕这四问展开。

## 1.2 技术内核：三类递进机制

| 方案 | 解决的问题 | 核心手段 | 判定方式 |
|---|---|---|---|
| BPMV（基础包级） | 路径可验证性 | 定长验证头 (f_s, f_k)；端口密钥 k_si = k_i ⊕ k_i^in ⊕ k_i^out；随机数 r_i；逐跳更新 | 控制器按候选路径逐条重算并比对 |
| CPMV（一致性增强） | 多路径验证结果不一致、控制器开销随路径数增长 | 在多路径汇聚节点注入补充验证信息 SVI，使不同合法路径输出一致 | 一次模幂比对替代 N 次路径遍历 |
| CFMV（流级压缩） | 交换机存储与控制器通信开销 | 出口交换机按流累加验证信息，包级 → 流级 | 累积等式一次判定整条流 |

申报书给出的关键公式（编号沿用原文）：

- (1) w = lcm(p1−1, p2−1)
- (2) k_si = k_i ⊕ k_i^in ⊕ k_i^out
- (3) (f_s, f_k) ← (g^(s_i·r_i) mod p2, g^(k_si·r_i) mod p2)
- (4) ∣H∣ = O(1)
- (5)(6) g^(w·s_m) mod p2 = f_s^w mod p2；同构于 k 分量
- (7)—(10) VI_s ← (f_s + VI_s) mod p2 等四式（流级累加）
- (11)(12) VI_s mod p2 = (g^(s_m) · VI_rs) mod p2 等（控制器侧流级判定）
- (13) g^x mod p2 = g^(x mod φ(p2)) mod p2（欧拉优化）

## 1.3 申报书给定的工程约束

- 定长验证头：∣H∣ = O(1)，不随跳数与路径数增长
- 原型平台：Mininet + Ryu 控制器
- 评测指标：验证准确率、控制器验证时间、交换机存储开销、验证头处理时间、通信开销、异常节点定位成功率
- 阶段划分：2026.05—12 调研与方案设计；2027 全年机制实现；2028.01—04 评测与结题

## 1.4 与已有工作的三条差异（答辩主线）

1. **验证对象**：从"单一路径"变为"合法路径集合"，这是与 Icing、Hummingbird、L-PVS 的根本分野。
2. **控制开销**：从"多路径多次验证"变为"多路径一次验证"，靠 SVI 把路径数从乘法项降为常数项。
3. **结果粒度**：从"发现异常"到"定位到交换机"，把验证结果转成可运维信息。

# 二、工程化转译（WBS）

申报书的研究内容需要落成可验收的模块，否则"实现 BPMV/CPMV/CFMV"无法判断完成度。拆解如下：

| 编号 | 模块 | 输入 | 输出 | 验收标准 |
|---|---|---|---|---|
| W1 | 数学内核 | 公式 (1)(2)(3)(5)(7)—(13) | mpv/core 纯 Python 实现 + 单元测试 | 合法路径通过率 100%，篡改路径检出率 100%（10^5 随机用例） |
| W2 | 拓扑与多路径 | 拓扑描述文件 | k-最短路径集 P_f、组表下发 | 线性 4/8/16 跳与 fat-tree(k=4) 上路径数与 OVS 组表实际一致 |

| W6 | 实验平台 | 上述全部 | 拓扑、流量、注入、采集、作图脚本 | 一条命令复现全部图表 |

## 3.3 端到端数据流

1. 控制器启动：生成 p1、p2、g、w；为每台交换机下发身份密钥 k_i 与各端口密钥；计算候选路径集 P_f。
2. 流表下发：源到目的按 P_f 建立多路径（组表 select 或显式多条流表）。
3. 入口交换机：初始化验证头 (f_s, f_k)。
4. 中间交换机：H_i = H_(i−1) ⊗ K_i，逐跳更新，头长恒定。
5. 汇聚节点：注入 SVI，使不同合法路径的输出统一。
6. 出口交换机：上报验证头，或按流累加后上报流级变量。
7. 控制器：一次模幂比对，输出合法 / 异常。
8. 判定异常：沿候选路径二分分段探测，缩小到 S_bad。

## 3.4 验证头承载方案（原型关键决策）

| 方案 | 载体 | 保真度 | 实现成本 | 结论 |
|---|---|---|---|---|
| A. MPLS 标签栈 | OVS push_mpls / set_field | 中（20 bit/标签） | 低，当天可跑 | 主线 |
| B. VLAN + DSCP 拼接 | 既有字段碎片拼装 | 低 | 低 | 备选 |
| C. BMv2 + P4_16 | 自定义报文头 | 高 | 高（需 p4lang 工具链） | 后期增强 |

选 A 的理由：OVS 3.3 原生支持标签栈操作，环境当天可通，能最快产出功能与开销数据。代价是 OVS 无法在被匹配字段上做模运算，由此引出风险 R4 的"控制/数据解耦"实现策略。

# 四、关键风险与对策

本计划的重点不在复述方案，而在**提前锁定四个会让项目空转的技术断点**。

## R1 数学闭合性（P0，必须在 M0 关闭）

**问题**：式 (5) 为 g^(w·s_m) mod p2 = f_s^w mod p2，其中 w = lcm(p1−1, p2−1) 是 p2−1 的整数倍。当 gcd(g, p2) = 1 时由欧拉定理有 g^(p2−1) ≡ 1 (mod p2)，故 g^w ≡ 1，于是

f_s^w = (g^(s_i·r_i))^w = 1

等式两端恒为 1，**任何路径（含被篡改路径）都会通过验证**，机制失去判别力。

**对策**：M0 阶段用不超过 50 行的 Python 反例脚本把上述结论固化为可执行证据，同时把"如何在不暴露 r_i 的前提下消去随机项"作为第一个理论攻坚点。三条可行方向：

1. 让随机项可消：令 r_i = r^(a_i)，控制器与数据平面共享 r 的幂次结构，使累积项与期望项同底对齐。
2. 改用双线性对 + 路径签名：控制器持有私钥而非仅公开 g，验证式变为配对检查。
3. 增加"随机项剥离"跳：令 f_s' = f_s^(r^(−1))，把 r 从指数中移出。

**验收**：先构造性证明"存在可达伪路径通过"，再给出修正公式并通过 10^5 随机用例。

## R2 逐跳更新算子缺失且表述矛盾（P0）

**问题**：申报书给了入口初始化式 (3) 与定长约束 (4)，但**没有给出中间交换机的更新公式**；正文又称"非交换性二元组乘法"，而 Z_p2 上的模乘是可交换的，无法把路径**顺序**编码进结果。

**对策**：把 H = (f_s, f_k) 视为 GL(2, Z_p2) 上的矩阵 M(H)，⊗ 定义为右乘每跳矩阵 K_i。矩阵乘法非交换，可编码顺序；代价是每跳 8 次模乘，需在 W4 做时延评估。

**验收**：顺序敏感性测试——交换两条路径上的交换机顺序，验证结果必须不同。

## R3 控制器选型（P1）

**问题**：Ubuntu 24.04 自带 Python 3.12；Ryu 4.34 依赖 eventlet < 0.31，在 3.12 上无法运行。这是"装不上 Ryu"的直接原因，不是操作问题。

**对策**：三级降级方案，M0 内实测确定。

1. 首选 os-ken（OpenStack 维护的 Ryu 衍生分支，API 基本兼容，对新 Python 支持更好）。
2. 备选 Python 3.11 虚拟环境 + 原版 Ryu。
3. 兜底自研最小 OpenFlow 1.3 控制器（仅实现 hello/features/flow_mod/group_mod/packet_in 五个交互），代码量约 600 行，反而更可控。

**验收**：控制器能起、能与 Mininet 建链、能下发流表并收到 packet_in。

## R4 数据平面无法执行模运算（P1）

**问题**：OVS 动作集只有 set_field、add、组表、output 等，无法计算 g^(x) mod p2。任何"逐跳模幂累加"都无法在纯 OVS 上如实完成。

**对策**：控制面与数据面解耦，功能与性能分两条路取证。

- **功能正确性**：OVS 负责真实转发与多路径，逐跳验证代理（packet-in/out 或镜像端口）负责头字段改写，语义保真。
- **性能数据**：控制平面时延用真实测量；数据平面开销用微基准（单次模乘耗时）+ 解析模型外推，并在图表中明确标注来源。
- **高保真分支（可选）**：M5 后若时间允许，用 BMv2 + P4 实现自定义头版本。

**纪律**：论文与报告中不得把"模型值"表述为"实测值"。这是评审最容易追问的点。

## R5 资源约束（P1）

虚拟机 20 GB 磁盘已用 78%，仅剩 4.2 GB；内存 3.8 GB（可用约 2.4 GB）。

**对策**：清理 /var/log（236 MB）与 /var/cache/apt（268 MB）可回收约 0.5 GB；实验拓扑上限定为 fat-tree k=4（16 台交换机）与线性 16 跳；单组实验并发流不超过 1000。若后续需 k=6，再考虑磁盘扩容到 40 GB。

## R6 软件源可达性（P1，已实测）

VM 内直连 pypi.org 超时（且仅解析到 IPv6，本机无 IPv6 路由）；清华 TUNA 与阿里云镜像返回 200。

**对策**：provision 阶段全局写入 pip index-url 与 apt 镜像，并在脚本中固化，保证换机可复现。

## R7 基线可比性（P2）

Icing、Atlas、L-PVS 均无开箱即用的可执行代码，直接"跑别人方案做对比"不现实。

**对策**：改为"同拓扑、同流量下的解析开销对照 + 关键算子微基准"，并在论文中明确对比口径，避免被质疑基线不可信。

# 七、实验设计

## 7.1 拓扑

| 编号 | 拓扑 | 规模 | 用途 |
|---|---|---|---|
| T1 | 线性链 | 4 / 8 / 16 跳 | 跳数敏感性 |
| T2 | fat-tree | k=4（16 台交换机） | 路径数敏感性 |
| T3 | 随机 Waxman | 20 节点 | 拓扑鲁棒性 |

## 7.2 变量与水平

- 候选路径数：1 / 2 / 4 / 8 / 16
- 路径跳数：4 / 8 / 16
- 流规模：10 / 100 / 1000 条流
- 异常类型：路径绕行、端口篡改、交换机旁路、流表篡改、乱序丢包

## 7.3 指标定义

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 验证准确率 | TP /(TP+FN) | 注入已知异常，统计判定结果 |
| 误报率 | FP /(FP+TN) | 正常流量下的误判 |
| 控制器验证时延 | 从收到上报到输出判定，取 P50 / P95 | 控制器埋点时间戳 |
| 交换机存储开销 | 每流状态字节数 + 流表项数 | ovs-ofctl dump-flows 统计 |
| 验证头开销 | 每包额外字节数 | 抓包比对报文长度 |
| 通信开销 | 控制消息条数与字节 | 控制器侧计数 |
| 定位成功率 | 命中真实异常交换机的比例 | 与注入点比对 |

## 7.4 异常注入手段

| 异常 | 注入方法 |
|---|---|
| 路径绕行 | ovs-ofctl mod-flows 修改出端口 |
| 端口篡改 | 改写流表 in_port 匹配条件 |
| 交换机旁路 | ip link set down 断链，走备用路径 |
| 流表篡改 | 直接修改组表 bucket |
| 乱序丢包 | tc netem delay / loss |

## 7.5 实验纪律

每组配置重复 3 次取中位数并给出 95% 置信区间；拓扑生成固定随机种子；每次实验记录 pip freeze 与内核版本；原始数据存 parquet，图表由脚本从原始数据生成，禁止手工修图。

过程中发现并解决两个问题：

1. **无终端提权失败**。非交互 SSH 下 `sudo` 报「a terminal is required」。
   解决：脚本抽出 `SUDO` 变量，自动化时传 `SUDO="sudo -A"` 并配 `SUDO_ASKPASS`，
   不修改系统 sudoers。
2. **CRLF 破坏脚本**。Windows 侧写入的文件带 `\r\n`，bash 报
   `set: pipefail: 无效的选项名`。解决：同步前统一转 LF，并加 `.gitattributes`。
